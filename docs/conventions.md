# Конвенции разработки

Обязательные паттерны для этого проекта. История и статус проекта — в [game-plan.md](game-plan.md).

## Структура компонента

Каждый компонент (и экран) живёт в своей папке, названной PascalCase по компоненту.
Вход — `index.tsx`:

```
src/components/ProblemCard/
  index.tsx        # сам компонент: структура и логика, ничего лишнего
  texts.ts         # все тексты компонента — переменными
  styles.ts        # все классы компонента — константами
  index.test.tsx   # тесты в той же папке
```

- Импорт всегда по папке: `import { ProblemCard } from '@/components/ProblemCard'`
  (перемещение файлов внутри папки не ломает импорты).
- Экраны (`src/screens/*`) подчиняются тому же паттерну.
- **Один компонент — один файл.** В `index.tsx` живёт ровно один компонент; определять
  вспомогательный компонент в файле другого — запрещено. Не пихать всё в один компонент.
- **Папки компонентов не вкладываются.** Папка компонента не может содержать другие папки
  компонентов. Все компоненты лежат плоско в своём слое: `src/components/<Name>/`
  (и одноразовые, и переиспользуемые — одноразовый переезжает в «свой» слой, когда появится
  второе использование), составные блоки — `src/features/<Name>/`. В папке экрана — только
  `index.tsx` + `texts.ts` + `styles.ts` (+ тест), никаких подпапок.

## Тексты

- Все пользовательские строки — переменные в `texts.ts` рядом с компонентом:

  ```ts
  export const texts = {
    startButton: 'Начать забег',
    aden: (n: number) => `адена: ${n}`,
  } as const;
  ```

- В JSX — только `texts.xxx`, никаких строк-литералов на экран.
- Подстановки значений — функциями (как `aden` выше).
- Единственное исключение — доменные подписи сложности (`label`, `hint`): это данные
  декларативного конфига ядра `src/game/difficulty.ts`, они уже переменные; компоненты
  берут их оттуда и не дублируют.
- Это же — задел на i18n: когда понадобится, `texts.ts` превращается в словарь одним
  движением, без выуживания строк из JSX.

## Стили

- Все классы — константами в `styles.ts` рядом с компонентом:

  ```ts
  export const styles = {
    root: 'flex flex-col items-center gap-10 py-10',
    optionActive: 'border-accent/70 bg-accent/15 text-accent',
  } as const;
  ```

- `index.tsx` остаётся чистой структурой/логикой — классы в нём не пишем.
- Условные комбинации собираются в JSX через хелпер: `cn(styles.option, active ? styles.optionActive : styles.optionIdle)`.
- Цель папки компонента: **всё, что относится к компоненту, лежит в одной папке** —
  `index.tsx` (структура), `texts.ts` (тексты), `styles.ts` (стили), тесты.

## Иерархия слоёв и правило переиспользования

Слои снизу вверх (импорты разрешены только вниз, никогда вверх):

```
src/
  game/        # чистое ядро (без React/DOM) — нижний слой
  lib/         # утилиты и хуки без бизнес-контекста (cn, format, random, hooks/)
  stores/      # сторы и экшены сессии
  components/  # переиспользуемые UI-компоненты
  features/    # составные блоки (компонент + логика), появится по надобности
  screens/     # экраны — точки композиции, верхний слой
  app/         # точка входа: роутер (не слой)
```

**Правило 2+ использований:** если компонент, метод или хук используется в двух и более
местах — он выносится в ближайший подходящий слой по своей природе:

- утилита / хук → `lib/` (хуки — в `lib/hooks/`);
- переиспользуемый UI → `components/`;
- составной блок с логикой (например, «этап башни» целиком) → `features/<Name>/`.

Одноразовый код живёт рядом с потребителем (в папке экрана/компонента) и поднимается
вверх в момент второго использования. Копии вместо импорта из общего слоя — запрещены.

## Ядро игры (src/game/)

Классовая архитектура с фабриками (решение 2026-11-04; `game/` по-прежнему без единого
импорта React/DOM):

- **Один класс — один файл**, файл называется по классу в PascalCase
  (`problem/Problem.ts`, `entities/Game.ts`).
- Сущности: `Game / Player / Floor / Level / Monster / Problem`.
  **Floor — этаж-локация** (владеет монстрами, их состав — по бюджету уровня),
  **Level — уровень сложности** (не локация! вычисляется из этажа, владеет формулой
  бюджета монстров и доступных рангов). Каждый уникальный монстр — свой класс
  (`monsters/Porta.ts` обычный ранг 1, `monsters/Mordeo.ts` ядовитый ранг 2);
  у игрока, монстров и этажей — расширяемые статы/параметры.
- **Все методы вычисления сущности лежат в её классе.** Фабрики (`ProblemFactory`,
  `FloorFactory`, `MonsterFactory`) создают сущности из декларативных конфигов.
- **Методы не мутируют** — возвращают новый экземпляр (предсказуемость + корректная
  работа стора на селекторах).
- Новые темы задач: расширить union `TopicId` + добавить запись в реестр `ProblemFactory`
  (тип `Record<TopicId, ProblemGenerator>` укажет компилятором на незарегистрированную тему).
  Новые операции — расширением union `Operation` в `difficulty.ts`.
- Сериализация: у каждого класса `toJSON()` + статический `fromJSON()`.
- Детерминизм: rng и время — только параметрами, не изнутри классов.
- Стейт хранит экземпляры классов (`{ game: Game }` в сторе), UI читает селекторами.
