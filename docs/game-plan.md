# Math — концепт игры и стек (v0, 2026-11)

## Игра

Тренажёр устного счёта в обёртке раннер-roguelite: игрок убегает от поднимающейся лавы по башне,
этажи проходятся верными ответами на примеры, монстры убиваются ответами. Ошибка или таймаут —
урон/смерть, после смерти — таблица рекордов.

Главная фишка: всё считается **в уме**. Примеры подбираются так, чтобы требовать устной работы
(переход через разряд: `47 + 54`, `62 − 28`), а не тривиальщины (`1000 − 1000`).

## Фазы разработки

### Фаза 0 — MVP (делаем сейчас)
- Экраны: меню → игра → game over.
- Настройки (один экран, рядом друг с другом):
  - **сложность**: easy / medium / hard → декларативный конфиг (диапазоны чисел, операции, лимиты);
  - **режим ввода**: свободный ввод цифрами | 4 варианта, один верный.
- Генератор: `a ± b`. Правила подбора: без вырожденных (`a + 0`, `a − a`), переходы через разряд
  на medium+, ответ ≥ 0.
- Цикл: верно → **+1 балл**, следующий пример; неверно → **game over** → главное меню.
- Лидерборд локальный (localStorage): видно после смерти и из меню.

Ориентиры сложностей:
- easy: `a, b ∈ 2..20`, без перехода через десяток, ответ ≥ 0;
- medium: `a, b ∈ 11..99`, приветствуется переход через разряд (`47 + 54`, `62 − 28`);
- hard: до 3-значных, вычитание с заимствованием, позже — таймер на пример.

#### Наследие из math-vite (проба пера, 2026-11-03)

Код не переносим — переносим решения:

- тулчейн подтверждён на этой машине: Vite 7.1 + React 19.1 + TS 5.9 + pnpm;
- «aden» как счётчик очков — оставляем название;
- неверный ответ = −1 сек вместо мгновенной смерти — мягкая альтернатива из пробы;
  в MVP по спеке остаётся смерть, мягкий режим потом станет настройкой (одна ветка в FSM);
- каркас экрана игры (поле player/enemy, вопрос, 4 кнопки ответа) — композиция рабочая.

Чего из пробы не берём (и почему): Context+useState вместо стора (перерисовки, нет доступа
снаружи Реакта), `setInterval` на module-level переменной (утечки, дрейф, фриз в фоновой
вкладке) — таймеры на timestamps, `useMemo([trigger])`-генератор — чистый seeded-генератор
в ядре, CSS-модули — Tailwind (ради NativeWind/RN), page-switching на useState — TanStack Router.

### Фаза 1 — Башня Крумы и лава

Сеттинг — Башня Крумы из Lineage 2: монстры, рейд-боссы (Archon Suscepter → Carnamakos → Core),
сундуки (включая взрывающиеся), палитра и музыка — в [art-direction.md](art-direction.md).
Тон всех текстов — насмешливый и подтрунивающий.

- **Глобальное время (лава)**: начальный запас **10 секунд**, тикает раз в секунду, на весь
  забег не сбрасывается. Быстрые верные ответы → игрок убегает от лавы. Запас кончился —
  лава догнала. (Архитектурно: секунды выводятся из timestamp'ов — дедлайны в данных,
  «тик» — производная, а не setInterval в стейте.)
- Этажи с дверями: верный ответ открывает дверь, игрок поднимается выше.
- С некоторого этажа — **монстры**:
  - **локальный таймер этажа**: успел ответить верно → урон монстру; не успел/ошибся →
    монстр бьёт игрока (правила удара — ниже);
  - сила и HP монстров растут с уровнем сложности;
  - **яд**: локальный таймер стартует «в минусе» на величину яда.

#### Реализация (2026-11-04, вечер — фаза 1 собрана, 62/62 теста)

- ① этажи-двери-подъём + лестница математики `configForLevel`;
- ② лава: 10с старт / +5 за этаж / кап 30с / тик wall-clock без пауз / endReason `lava`;
- ③ бои: каждый 3-й этаж, монстр сам не бьёт — пример; таймер ответа с ядом; таймаут = удар;
- ④ урон/щит/яд: инвариант «яд ⇔ урон коснулся HP», стак+1 за отравляющий удар,
  длительность 3 этажа, срез секунд с локального таймера;
- ⑤ предметы: бутыли/пластины/ядра (тап-иконки), сундуки на каждом 5-м этаже
  (~20% ловушки), заморозка мира (лава + таймеры стоят, игрок действует);
- endReason: `wrong | surrender | lava | hp`; на дверях ошибка фатальна, в бою — удар.

#### Финальные решения (2026-11-04, вечер — закрыли все открытые вопросы)

- **Режим один**: никакого «тренинга». Меню = выбор варианта ввода + «начать игру».
  Настройка сложности из меню **убирается** — сложность нарастает сама уровнями.
- **Математика растёт с уровнем сложности (Level), не с этажом.** Лестница:
  ур.1 — `+`; ур.2 — `+ −`; ур.3 — `+ − ×`; ур.4 — `+ − × ÷` (деление **только нацело**,
  без дробей и десятичных); ур.5 — добавляется **третье число**; ур.6+ — **микс знаков**
  в одном примере; дальше растут количество чисел и диапазоны.
- **Адена — просто очки**, никуда не тратятся; зарабатываются с масштабом от сложности.
- **Бой**: монстр сам не атакует — просто идёт пример. Верный ответ = удар игрока по монстру;
  неверный = удар монстра по игроку (дальше — правила щита/яда ниже). Смерть: HP=0 или лава.
- **Предметы — тап-иконки** (мобильный экран, никаких хоткеев); крупные удобные кнопки.
- **Стартового набора нет** — предметы только из сундуков по этажам.
- **Паузы нет НИКОГДА**, включая свёрнутую вкладку — иначе читерство («запомнить пример
  и решить вне игры»). Время — по wall-clock: при возврате во вкладку недостающие секунды
  догоняются одним применением.
- **Музыка** — отложена до отдельного решения.

Микро-дефолты (взяты ассистентом, легко меняются): адена за верный ответ = номер уровня;
на этаже с несколькими монстрами бой идёт с первым живым по очереди; сундуки открываются тапом.

#### Урон, щит и яд (правила удара монстра)

Урон удара = сила монстра. Порядок поглощения:

1. есть щит → урон в щит;
2. щит сломан и урон больше остатка щита → остаток урона в HP **и применяется яд**;
3. щита нет → урон в HP (яд применяется);
4. щит поглотил весь урон → **яд не применяется**.

Инвариант: **яд применяется тогда и только тогда, когда урон коснулся HP.**
Щит — запасные HP «с бонусом от яда»: полный блок глотает и урон, и отравление.

#### Предметы (система активных вещей — задел)

- **Ядра заморозки** (активные): замораживают лаву **и** локальный таймер этажа. Это **не пауза,
  а заморозка мира**: заморожено всё вокруг, а игрок продолжает действовать (решать, отвечать).
  Единственная механика, приостанавливающая таймеры (модалка сдачи — никогда).
- **Бутыль против яда**: свойство «сила» — сколько яда снимает (сейчас: одна бутыль, снимает весь яд).
- **Бутыль лечения**: свойство «сила» — сколько HP восстанавливает (сейчас: одна, лечит всё).
- **Щитовые пластины**: щит — слой HP поверх здоровья, поглощает урон до HP и блокирует яд.

На подумать (кандидаты): песочные часы (+сек к глобальному времени), свиток ускорения
(+сек к локальному таймеру), соулшоты (двойной урон по монстру — привет L2), мантия
(поглотить одно отравление), благословенный свиток (одно воскрешение с 1 HP), карта этажа
(пропустить одну дверь), адена-магазин между забегами (мета-прогресс).

#### Решения по механикам (2026-11-04, ответы на открытые вопросы)

- **Пополнение глобального времени — при переходе на новый этаж.** Константу подбираем
  эмпирически: десятки итераций с ростом сложности; стартовая гипотеза **+5 сек/этаж**
  (`GLOBAL_TIME_PER_FLOOR`, тюнинг после плейтестов).
- **Источники яда — только ядовитые монстры (Mordeo) и сундуки-ловушки.** Они наносят
  обычный физический урон **и** накладывают яд. Сам яд урона не наносит — он сокращает
  шкалу локального времени на ответ.
- **Яд стакается**: каждый отравляющий удар **+1 яда**; наложение обновляет время действия;
  действие растянуто на несколько комнат. Нужен наглядный индикатор игроку (сколько яда
  накоплено и на сколько комнат его хватит).
- **1 щитовая пластина = +1 щита** — подтверждено.
- **Меню «вход в Круму»** — анимированная канвас-сцена: силуэт башни, светящийся портал,
  живой огонь факелов, тлеющие угольки, ползущий туман. Реализовано процедурно, без
  ассетов (`components/CrumaEntranceBackground`); фолбэк — статичная картинка.
- **Этажи-сокровищницы** без примеров: сундуки (лечение / артефакты / улучшения). Общее время
  продолжает идти.
- **«Сдаться» (SOE)** — реализовано уже в MVP: модалка подтверждения **не ставит игру на паузу
  никогда** (время — глобальное и локальное — продолжает идти); «Сбежать» завершает забег,
  адена сохраняется.

### Фаза 2 — мета
- Лидерборд: локальный сейчас → серверный вместе с бекендом.

### Фаза 3 — realtime-мультиплеер
- Чистое игровое ядро (см. архитектуру) переиспользуется как авторитетная логика на сервере.

## Архитектура — главное решение

Обязательные паттерны разработки (папка на компонент, `texts.ts` с текстами-переменными и т.д.) —
в [conventions.md](conventions.md).

Ради миграции на RN игровая логика — **чистый TypeScript без единого импорта React/DOM**:

```
src/
  game/            # ЧИСТОЕ ЯДРО: без react, без window, без localStorage
    rng.ts         # seeded PRNG (mulberry32) — детерминизм
    generators/    # ProblemGenerator: арифметика сейчас; тригонометрия, производные — потом
    difficulty.ts  # декларативные конфиги сложностей
    fsm.ts         # конечный автомат матча: (state, action) => state
    types.ts
  stores/          # @tanstack/react-store: settings, session
  screens/         # menu, game, gameover, leaderboard, settings
  components/      # ui (shadcn) + игровые компоненты
  lib/             # storage-адаптер, утилиты
```

Правила:
1. `game/` не импортирует React — никогда. Экраны подписываются на стор и дёргают `dispatch(action)`.
2. Таймеры — на timestamp (`performance.now()`), а не на инкрементах: так паузы, фризы и яд
   (старт таймера «с минуса») обрабатываются вычитанием отрезков, а не костылями.
3. Сложность и режим ввода — данные (конфиг), а не код: новый предмет = новый генератор за тем же
   интерфейсом, движку игры всё равно, что спрашивать.
4. Позже `game/` переезжает в `packages/game-core` (pnpm workspaces) и подключается к Expo как есть.
   Для мультиплеера тот же FSM станет серверной (авторитарной) логикой.
5. Ядро — **классовая архитектура с фабриками** (решение 2026-11-04, сменило ранний вариант
   «чистые функции»). Расширяемость — приоритет №1: «добавить что-то куда-то без страха, что
   код сломается». Типизация, расширяемость, предсказуемость; union-типы приветствуются.
   - Классы сущностей: **Game / Player / Floor / Level / Monster**. Различаем:
     **Floor — этаж-локация** (текущее место в башне, владеет списком монстров),
     **Level — уровень сложности** (растёт по мере преодоления этажей; владеет вычисляемым
     бюджетом монстров и доступными рангами). Каждый уникальный монстр — отдельный класс
     (Porta — обычный ранг 1; Mordeo — ядовитый ранг 2; новые — наследованием + записью
     в реестр рангов `MonsterFactory`). Состав монстров этажа = случайное разбиение бюджета
     уровня на ранги (бюджет 3 → [1,1,1] или [2,1]). У игрока, монстров и этажей появляются
     статы, параметры, способности.
   - Все методы вычисления конкретной сущности лежат **в самом классе**.
   - Фабрики создают сущности из декларативных конфигов (уровень N → уровень/монстры).
   - В стейте хранятся экземпляры классов и результаты их работы.
   - Новые виды примеров, статов и эффектов добавляются через union-типы и реестры (open/closed),
     не правкой существующей логики. Полная лестница тем — [math-topics.md](math-topics.md)
     (арифметика → приёмы → алгебра → комбинаторика → геометрия/тригонометрия → матанализ →
     дисциплины чемпионата мира).
   - Сохраняем при этом: детерминизм (rng и время передаются аргументами, не берутся изнутри
     классов) и сериализуемость (toJSON/fromJSON у каждого класса — персист забега и
     мультиплеер остаются доступны).
6. Танстек в RN: Store переезжает как есть (ядро агностично, React-биндинг на
   `useSyncExternalStore`, работает в RN с React 18+), Query поддерживает RN официально,
   Router — пока без стабильного RN-релиза (активная работа, показан на Expo в 2026-02).
   Роутинг у нас и так платформенный слой, потери нет.

## Состояние: где живёт контекст игры

Без бека и в рамках одной сессии персист не нужен вовсе — **всё в памяти**.

Два стора-синглтона на уровне модуля (`@tanstack/react-store`), без Provider и без React Context:

- `settingsStore` — сложность, режим ввода;
- `sessionStore` — текущий забег.

```ts
interface SessionState {
  status: 'idle' | 'running' | 'gameover';
  seed: number;          // seed текущего забега
  problem: Problem | null;
  score: number;
  stats: { correct: number; wrong: number; bestStreak: number };
  lastAnswer: 'correct' | 'wrong' | null;
}
// фаза 1 добавит туда же: floor, playerHp, monster, runStartedAt, floorDeadline, poison
```

Поток данных: UI → `dispatch(action)` → чистый `reduce(state, action)` из `game/fsm.ts` →
`sessionStore.set(next)`. Компоненты подписываются селекторами
(`useStore(sessionStore, s => s.score)`) — частые апдейты и тики таймеров не перерисовывают всё дерево.

Следствия:

- стор — синглтон модуля и переживает переходы между роутами: «выйти в меню и вернуться»
  сохраняет забег бесплатно;
- обновление страницы = новая сессия (в рамках текущего скоупа так и задумано);
- когда понадобится персист — один подписчик стора → адаптер, точка изменения одна;
- React Context для состояния не используем: он перерисовывает поддерево целиком и не читается
  снаружи Реакта (rAF-цикл, гарды роутера). Context зайдёт позже только как DI сторов в тестах.

## Генерация примеров: библиотека или своё

Прошерстили npm (2026-11): живой библиотеки-генератора математических примеров нет.

- единственный кандидат `@yeungon/math-generator` — последняя публикация январь 2023,
  ~11 скачиваний в месяц;
- `math-generator` — не существует (404 в registry);
- остальное — не генераторы: `mathjs` / `math-expression-evaluator` — вычислители выражений,
  `remark-math` / `katex` — рендер формул, `random` / `seedrandom` — RNG.

Генерация примера для тренажёра — это не математика, а геймдизайн: «переход через разряд»,
дистракторы вида ±1/±10/перепутанные цифры, запрет вырожденных случаев. Это правила нашей игры,
в чужой библиотеке их не будет.

Решение:

1. MVP: свой генератор арифметики, ~50 строк (randint с ограничениями + дистракторы), ноль
   зависимостей, всё под юнит-тестами;
2. сложные темы (тригонометрия, производные) — подключаем **mathjs** (15,7 млн скачиваний/мес,
   активно поддерживается) как вычислитель внутри нашего же интерфейса: `derivative()`,
   `simplify()`, `evaluate()`. Переиспользуем математику, а не генерацию;
3. RNG — свой mulberry32 (6 строк, seeded — задел на мультиплеер), без зависимостей.

### Интерфейс генератора (уже под расширение)

```ts
interface Problem {
  prompt: string;        // «47 + 54» — готовая к показу строка
  a: number;
  op: '+' | '-';
  b: number;
  answer: number;
  options: number[];     // 4 перемешанных варианта, всегда содержит ответ
  distractors: number[]; // 3 правдоподобных неверных
}

interface ProblemGenerator {
  generate(rng: Rng, cfg: DifficultyConfig): Problem;
}
```

Дистракторы: ответ ±1, ±10, ±2, перепутанные разряды — уникальные, на лёгких без отрицательных.

## Канвас и физика

Короткий ответ: до фазы с богатой визуалкой лавы — **ничего**. Весь текущий геймдизайн — вёрстка
и анимации: лава — визуализация таймера (уровень = f(timestamp)), двери/монстры/урон — твины
(motion). «Движение на экране» — не физика; физики как модели (гравитация, коллизии) в дизайне нет.

Когда канвас реально понадобится (сотни партиклов, шейдеры, свечение лавы):

1. сначала дожимаем SVG/CSS + motion — обычно этого хватает;
2. веб-выбор — **PixiJS v8** точечным эффект-слоём: ref-обёртка в компоненте, HUD остаётся в DOM
   (или `@pixi/react`). Осознанно платформенный код: на RN эффекты перепишутся нативно, ядро не меняется;
3. RN-совместимый канвас (react-native-skia) — под вопросом: Shopify уходит из RN, спонсорство
   Skia до конца 2026, дальше форк автора под новым именем. Не смерть, но неопределённость —
   стратегию на него не ставим.

Физика — только если появится механика, которой она реально нужна (снаряды, платформинг):

- **matter-js** — 2D, крошечный, renderer-agnostic (DOM / Pixi / Skia / RN);
- **Rapier2d** (WASM) — мощнее и детерминированный (важно, если физика попадёт в сетевую
  авторитарную логику; для квиз-мультиплеера не попадёт).

Движки (Phaser, Three/R3F) — нет: свой game loop и сцены конфликтуют с React-подходом и RN.

## Риск-заметка: React Native и Shopify (2026-09)

Shopify переводит свои приложения обратно на натив (Swift/Kotlin) и прекращает с конца 2026
спонсорство React Native Skia и Restyle (Skia продолжится форком автора под новым именем).
RN жив (Meta + Expo), но тренд смещается к двойной нативной разработке с ИИ-агентами.

Наш ответ уже зашит в архитектуру: чистое ядро `game/` + тонкий платформенный UI. Миграция
возможна в RN, в натив с портом ядра, или остаёмся вебом/PWA — решение можно отложить без переделок.
